## 0. この文書のスコープ

「SNS 投稿（配信）機能を別プロジェクトへ切り出し、本リポジトリはセカンドブレイン構築に一本化する」という方針転換に伴い、
**既存の OSS をそのまま使った場合に system-design.md の要件がどこまで満たされるか**を評価する。

評価から外した要件（配信側プロジェクトへ移設する想定）:

| 要件 ID | 内容 | 扱い |
|---|---|---|
| REQ-D-01〜05 | Zenn / X / dev.to / Note / YouTube への配信 | **配信プロジェクトへ移設** |
| REQ-A-02 / A-03 | 発信ネタ検出・チャネル別ドラフト生成 | **配信プロジェクトへ移設** |
| REQ-P-01〜03 | 公開前承認・秘匿情報ブロック・verbatim ブロック | **配信プロジェクトへ移設**（公開行為が無ければ発火しない） |
| REQ-U-02 | 自分の文体でドラフトが書かれる | **配信プロジェクトへ移設**（ただし `profile/voice.md` というデータ自体はセカンドブレイン側に残す） |

REQ-U-01（自分が何者か）・REQ-U-03（公開不可領域）は、**知識ベースが保持すべきプロフィール情報**として本評価に残した。

## 1. 調査方法

1. GitHub の topic 検索（`second-brain` / `knowledge-management` / `pkm`）を star 順に走査
2. 各候補の README・リポジトリツリー（MCP サーバの有無、インポータの有無、CI の有無）を直接確認
3. 外部前提（ChatGPT / Gemini の MCP 対応状況）は Web 検索で 2026-09 時点の状況を確認

star 数は「どれだけ使われているか」の代理指標に過ぎず、**要件適合の判断には使っていない**。

### 3.1 貯まる（G-1 / Capture）

| 要件 | 内容 | A | B | C | D | E |

| REQ-C-02 | **Gemini の会話を自動で登録できる** | × | × | × | × | × |
| REQ-C-03 | Claude チャットで得た知識を登録できる | ○ | ○ | ○ | **◎** | △ |
| REQ-C-04 | 手動メモを登録できる | ◎ | ◎ | ◎ | ◎ | ○ |
| REQ-C-05 | **同じ内容を何度投入しても重複しない（冪等キー）** | △ | △ | △ | △ | △ |
| REQ-C-06 | 過去の会話を一括取り込みできる | △ | △ | △ | **◎** | △ |
| REQ-C-07 | 任意のアプリからも登録経路がある | × | △ | △ | ◎ | ◎ |

補足:

- **REQ-C-01**: A と C は「vault ディレクトリで Claude Code を起動する」前提が強く、無関係な開発プロジェクトで作業中にその場で捕捉する経路が弱い。D（basic-memory）は MCP サーバとして常にクライアント側に居るため、どのプロジェクトで作業していても書き込める。
- **REQ-C-02**: **どの OSS も Gemini アプリの会話を自動で吸い上げる経路を持たない。** 本プロジェクトが設計した「Gemini に要約させ → Google ドキュメントへ出力 → GAS が検知 → GitHub Issue → 取り込み」という迂回路は、OSS 側に等価物が存在しない。
- **REQ-C-05**: 「同じ会話を 2 回投げても 1 件にする」という**明示的な冪等キー（`sourceId`）による重複排除は、どの OSS も持っていない**。A は出典を内容ハッシュで不変保存するため最も近いが、取り込み口での重複判定とは別物。B は「意味的に同じ話題なら既存ノートを書き換える」方式で、これは REQ-K-07（育つ）は満たすが REQ-C-05（二重取り込み防止）とは異なる。
- **REQ-C-06**: D は `src/basic_memory/importers/` に **ChatGPT エクスポート・Claude 会話エクスポート・Claude Projects の専用インポータを実装済み**。本プロジェクトで P3 に置いていた IMPL-L1-06 がそのまま手に入る。

補足:

- **REQ-K-02 / K-05**: A（claude-obsidian）は「出典台帳」と「主張台帳」を分けて持ち、各主張に**典拠・鮮度・支持 / 反証・確信度・レビュー状態**を保持する。本プロジェクトの `origin: self | external` より踏み込んだ実装で、外部由来知識の扱いという観点では設計の上位互換に近い。
- **REQ-K-07 / K-08**: B（obsidian-second-brain）の中核がまさにこれ。「新しい情報が来たら既存ページを**書き換える**」「矛盾は `/obsidian-reconcile` が調停する」を売りにしており、本プロジェクトが REQ-K-07 で最重要視した「育つ」を正面から実装している。
- **REQ-K-01 の ×（E）**: Khoj は既存文書に対する検索・対話レイヤーであり、**ノートを構造化して書く役割は持たない**。「貯まる」「出る」はあるが「知識化」が無い。

### 3.3 触れる（G-2 / Interface）— **今回もっとも重視された軸**

| 要件 | 内容 | A | B | C | D | E |
|---|---|:-:|:-:|:-:|:-:|:-:|
| REQ-I-01 | Obsidian で閲覧・編集できる | ◎ | ◎ | ◎ | ◎ | ○ |
| REQ-I-02a | **PC の他 AI クライアント（Codex / Cursor / Claude Desktop 等）から検索できる** | △ | ○ | ○ | **◎** | ◎ |
| REQ-I-02b | **スマホの Chat AI（ChatGPT アプリ / Gemini アプリ）から検索できる** | × | × | × | △ | △ |

**REQ-I-02b が本調査で最も重要な論点。** 2026-09 時点の外部事実:

- **ChatGPT**: Developer Mode で**リモート HTTPS の MCP サーバ**を接続できる（Plus / Pro で利用可能）。ただし個人プランは**読み取り専用**に制限され、書き込み可能な接続は Business / Enterprise / Edu のみ。ローカル stdio の MCP サーバには接続できない。
- **Gemini**: 一般向け Gemini アプリの独自 MCP 接続は **Spark 利用者の Spark タスク内のみ**。カスタム MCP サーバの正式接続は Gemini Enterprise (Business edition) 側の機能で、**公的に信頼された CA 署名の TLS 証明書と StreamableHTTP が必須**（自己署名は不可）。

つまり、**スマホの Chat AI から知識ベースに触るには「インターネットに公開された HTTPS の MCP サーバ」が必然的に要る**。これは system-design.md が P4 に置いた IMPL-L6-03（remote MCP）と同じ結論であり、同時に **REQ-N-01（常時起動マシン不要）と正面から衝突する**。
D（basic-memory）はこの矛盾を「月 $15 のホスティングを他人にやらせる」ことで解いている（自分は常時起動マシンを持たない）が、**知識ベース本体が第三者のインフラに乗る**ため、判断が要る。

| REQ-N-02 | LLM 実行がサブスク定額に収まる | ◎ | ◎ | ◎ | ◎ | △ |

補足:

- **REQ-N-01 / N-02 の × △（E）**: Khoj は Docker で常駐サーバを立てる前提であり、LLM も API 従量課金かローカル LLM。本プロジェクトの「常時起動マシン不要 + Claude サブスク定額」という 2 大前提を**両方壊す**。単体採用は不可。
- **REQ-N-06 / N-07 の ◎（A）**: claude-obsidian は「並列エージェントは vault を奪い合えない。ワーカーは下書きを返し、**単一のオーケストレータが 1 つの復旧可能なトランザクションとして適用する**」と明言し、変更前に必ず操作計画（JSON）を提示して SHA256 の承認を取ってから適用する。本プロジェクトの ownership-guard（IMPL-L0-04）と同じ問題意識を、より実装寄りに解いている。
- **REQ-P-04**: これはリポジトリ運用（private repo にする、CI で可視性を監視する）の話であり、**どの OSS の責務でもない**。自作範囲として残る。

## 4. 総括: どの OSS も埋めない「残る自作範囲」

星取り表の × と △ を集約すると、既存 OSS を全部足しても埋まらない穴は 5 つに絞られる。

| # | 残る穴 | 重大度 | 該当要件 | なぜ OSS に無いか |
|---|---|---|---|---|
| 1 | **Gemini / スマホからの自動捕捉**（要約 → Docs → GAS → Issue → 取り込み） | **【重大】** | REQ-C-02, REQ-N-03 | OSS はすべて「PC で CLI エージェントを起動する」前提。Gemini に書き込み口が無い問題を迂回する発想自体が存在しない |
| 2 | **常時起動なしで外部 Chat AI から到達する経路** | **【重大】** | REQ-I-02b, REQ-N-01 | ChatGPT / Gemini がリモート HTTPS MCP しか受け付けないため、原理的に「常時起動不要」と両立しない。有料ホスティングか scale-to-zero のサーバレス自作の二択 |
| 3 | **冪等キー（`sourceId`）による二重取り込み防止** | 【中】 | REQ-C-05 | OSS は「人間が手で投げる」前提なので、同じソースを機械が二度投げる事故を想定していない |
| 4 | **1 パス 1 書き手の CI 強制（ownership-guard）** | 【中】 | REQ-N-06 | claude-obsidian が実行時トランザクションで近いことをやっているが、CI で構造的に禁止する仕組みではない |
| 5 | **private / public 境界の機械的な保証（visibility-guard）** | 【中】 | REQ-P-04 | リポジトリ運用の責務であり OSS の対象外 |

**結論: 既存 OSS 単体では全要件を満たせない。** ただし、**満たされない範囲は当初設計の 3 割程度まで縮む。**
特に、本プロジェクトが P0-b 〜 P2 で自作しようとしていた「知識化（digest）」「ノートを育てる」「MOC 構築」「矛盾検出」「出典追跡」は、**層 3 の OSS がすでに実装済みで、しかも本設計より踏み込んでいる部分がある**。

## 5. 推奨構成と却下した選択肢

### 推奨: 層 3 の 1 本を「知識化エンジン」に、basic-memory を「他 AI への口」に据える 2 層構成

```
  スマホ Chat AI (ChatGPT / Gemini)          PC の AI クライアント
        │ リモート HTTPS MCP                  │ ローカル stdio MCP
        │ （★ここだけが未解決の穴）           │
        ▼                                    ▼
  ┌──────────────────────────────────────────────────┐
  │  basic-memory（MCP サーバ / 過去会話インポータ）    │  ← 他 AI からの読み書き口
  └──────────────────────────────────────────────────┘
        │ 同じファイルを読み書き
        ▼
  ╔══════════════════════════════════════════════════╗
  ║  knowledge-repo (private Git) — プレーン Markdown  ║  ← 唯一の正（変更なし）
  ╚══════════════════════════════════════════════════╝
        ▲ 知識化・ノート育成・MOC 構築・矛盾調停
  ┌──────────────────────────────────────────────────┐
  │  層 3 OSS（claude-obsidian または                  │
  │            obsidian-second-brain）+ Obsidian       │
  └──────────────────────────────────────────────────┘
        ▲ 自作で足す: capture CLI（冪等キー）/ GAS→Issue / CI ガード
```

**層 3 の 2 択の性格の違い**:

| | claude-obsidian (A) | obsidian-second-brain (B) |
|---|---|---|
| 強み | **出典・主張の台帳が厳密**。書き込みが単一トランザクションで壊れにくい | **ノートが自動で育つ**。矛盾調停・定期整理が本体機能 |
| 本設計との相性 | REQ-K-02 / K-05 / N-06 / N-07 に強い | REQ-K-06 / K-07 / K-08 に強い |
| 懸念 | vault ディレクトリ起動前提が強く、REQ-C-01（他プロジェクトからの捕捉）が弱い | 47 コマンド・8 プラットフォーム対応と表面積が大きく、把握コストが高い |

### 却下した選択肢

| 選択肢 | 却下理由 |
|---|---|
| **Khoj 単体に寄せる** | 常時起動サーバ必須（REQ-N-01 違反）+ LLM が API 従量（REQ-N-02 違反）。さらに「知識化して書く」機能が無く、G-2 の中核が空く |
| **SiYuan / AFFiNE / AppFlowy を器にする** | 保存形式が独自ストアであり、原則 P-1（Git のプレーン Markdown が唯一の正）を捨てることになる。Obsidian を View に据える現行方針の方が忠実 |
| **Logseq を器にする** | ファイルは Markdown だがアウトライン方言が強く、GitHub や外部 AI から素直に読める最大公約数から外れる |
| **mem0 / cognee / letta** | アプリに組み込む記憶ライブラリであり、**人間が Obsidian で読む知識ベース**ではない。REQ-I-01 が原理的に成立しない |

## 6.5. 実機検証で判明した制約と最終判断（2026-09-07 追記）

§5 で claude-obsidian を推奨したが、**実際に導入を試みた結果、この環境では採用できないことが判明した。**

### claude-obsidian が Windows で使えない理由

| 項目 | 内容 |
|---|---|
| 症状 | 既存 vault への非破壊導入（`adopt`）を適用しようとすると `ERR UNSUPPORTED_PLATFORM` で停止する |
| 原因 | 書き込みの安全性を **POSIX のディレクトリ記述子**に束縛しているため。書き込み中にフォルダやシンボリックリンクがすり替えられても別の場所へ書かないことを、この仕組みで保証している。Windows にはこの機構が無く、**弱い保証で黙って動くより最初から断る**という設計判断がされている |
| 影響範囲 | 読み取り・事前確認（dry-run）はネイティブ Windows でも動く。止まるのは `init` / `adopt` / `migrate` / `transaction apply` など**書き込みを伴う操作すべて** |
| 回避策 | WSL（汎用 Linux ディストロ）を導入して、そちら側から操作する |
| この環境の状況 | WSL には Docker Desktop 用の最小ディストロのみ。汎用 Linux は未導入 |

**皮肉な点**: §5 で claude-obsidian を推した第 2 の理由（書き込みの安全性）そのものが、Windows では利用不可能な形で実装されていた。**「安全性が高い」という評価は、その安全性がどの OS 前提で成立しているかまで確認しないと意味を持たない。**

### 最終判断: eugeniughelbur/obsidian-second-brain を採用

| 判断根拠 | 内容 |
|---|---|
| Windows 正式対応 | 2026-09 リリースの v0.15（The Port）で、Windows のパス形式・改行コード（CRLF）・BOM・UTF-8・`USERPROFILE` 基準の設定ファイル配置まで対応済み |
| 導入の軽さ | Claude Code のプラグイン追加 2 行で完了。work-stream 自身の配布形態と同じ |
| 前提条件 | Claude Code / git / uv のみ。この環境には全て導入済み（`jq` は無いが、プラグイン経路では不要） |
| 星取り表上の強み | REQ-K-06 / K-07 / K-08（増えても破綻しない・育つ・矛盾統合）。MCP サーバも同梱 |

**採用に伴い受け入れた副作用**: この OSS は「AI-first」というノート規約（`## For future agent` の前書き、`[[wikilink]]` の必須化）を持つ。これは system-design.md の「リンク記法は標準 Markdown の相対リンク（`[[...]]` は GitHub や外部 AI で解決されないため）」という方針と**衝突する**。ノート構造は後から変えられる柔軟性を優先する、という方針転換に基づき、**当面は OSS 側の規約に従う**。GitHub 連携経由で外部 AI に読ませる際に `[[...]]` が解決されない問題が実害として現れたら、その時点で再評価する。
