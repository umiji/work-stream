# 知識集積・アウトプット自動化基盤 — Draft Proposal レビュー

対象: 2026-07 時点の Draft Proposal（Obsidian vs Notion 比較 / 実行環境比較 / アダプタ抽象化アーキテクチャ / MVP フェーズ計画）
レビュー日: 2026-07-10

## 総評

方向性は概ね妥当。特に **L1（ナレッジ基盤）と L4（配信）の 2 つのアダプタ境界を製品化の骨格と位置付けた判断は正しく**、「MVP は Obsidian 一択、将来ユーザーが基盤を選択」という結論も支持できる。

ただし以下の問題があり、このまま実装に入ると手戻りが発生する。

1. **【重大】原初要求にあった「ChatGPT / Claude chat の取り込み」が設計から抜け落ちている**（入力側のアダプタ境界が未定義）
2. **【重大】実行環境の評価が古い** — `claude setup-token` により headless / CI でのサブスク定額利用は公式サポート済みで、②③の Cons 評価と推奨の前提が変わる
3. **【重大】X API の無料枠は 2026 年 2 月に廃止済み** — 「投稿は無料枠で可」は成立しない

---

## 1. 【重大】入力側の抽象化が欠落 — 原初要求との不整合

原初要求には「ChatGPT や Claude chat のやり取りも MCP / API でナレッジ基盤にインプットしたい。MVP スコープ外でも**設計手戻りが無いように**」と明記されている。しかし Draft の L0 は「Obsidian daily note / inbox.md（将来: LINE Bot, 音声）」のみで、チャット履歴取り込みが構成図にもフェーズ計画にも現れない。**「手戻りが無いように」という要求そのものが未達**であり、これが本レビュー最大の指摘。

### 対応方針: CaptureAdapter 境界を今定義する

出力側（PublishingAdapter）と対称に、入力側にもアダプタ境界を切る。

```
interface CaptureAdapter {
  pull(since)            // 新規アイテムの取得（pull型）
  // push型ソース（webhook/bot）は共通の ingest エンドポイントに正規化して投げる
}

// 全ソース共通の正規化スキーマ（これを今決めることが手戻り回避の本体）
CapturedItem {
  sourceType     // claude-code | chatgpt | claude-chat | manual | voice | ...
  sourceId       // 会話ID + メッセージID 等。冪等キー（重複取込の排除に必須）
  capturedAt / originalTimestamp
  content        // Markdown 正規化済み本文
  thread?        // 会話の文脈（role, 順序）を保持するか要否を決める
  meta           // 元URL、モデル名、タグ候補 等
}
```

### 各ソースの現実解（2026-07 時点）

| ソース | 現実的な取得方法 | 備考 |
|---|---|---|
| Claude Code | ローカルセッションログ（`~/.claude/projects/*.jsonl`）を読むローカルアダプタ | 最も簡単。MVP に入れられる |
| ChatGPT | 公式に会話履歴取得 API は無い。エクスポート ZIP（conversations.json）の定期取込が現実解 | 「MCP で綺麗に取れる」前提は現状成立しない |
| Claude chat | 同様にデータエクスポートの取込 | 同上 |

**設計上の含意**: push 型（bot / webhook / MCP）だけでなく、**pull 型（エクスポートファイルの取込）を一級市民として設計しておく**こと。冪等キー（sourceId）による重複排除をスキーマに最初から入れておくこと（同じ会話を再エクスポートした際の dedup は後付けすると手戻りになる）。

---

## 2. 【重大】実行環境の評価が古い — `claude setup-token`

Pro / Max サブスクユーザーは `claude setup-token` で **1 年有効の OAuth トークン**を発行でき、`CLAUDE_CODE_OAUTH_TOKEN` として headless 環境や CI で**サブスク定額のまま**利用できる。公式の claude-code-action もこのトークンをサポート済み。

これにより Draft の比較表は次のように変わる:

- **② クラウド VPS**: 「headless での OAuth ログイン維持が手間」→ ほぼ解消。トークンを置くだけ
- **③ GitHub Actions**: 「実質 API キー = 従量になりがち」→ **誤り**。Max サブスクで公式に動く。定額適合は △ ではなく ○〜◎
- **結論への影響**: ① ローカル常時起動機の推奨自体は依然妥当（vault がローカルにあり同期不要、Playwright が動く、追加費用ゼロ）。ただし「常時起動機が無いと始められない」わけではなく、**マシンを用意せず Actions だけで P1〜P3 を定額で回す構成も成立する**。ローカル機の調達を前提にしたロードマップは再考の余地あり

### 追加の注意: 「定額 = 無制限」ではない

Max プランには 5 時間ローリング + 週次の使用量上限がある。夜間バッチ・cron 実行はこの枠を消費するため、対話利用と食い合う。バッチの実行頻度・処理量はレート消費を平準化する前提で設計すること（Draft にはこの観点が無い）。

また **P5（製品化）でユーザーのサブスクに乗ることは不可能**（setup-token は個人アカウント紐付け・共有禁止）。製品化フェーズでは API 従量 + 課金転嫁が前提になることを P5 の前提条件として明記すべき。

---

## 3. 【重大】X API 無料枠は廃止済み（2026-02）

2026 年 2 月に X API はティア制から pay-per-use に移行し、**新規開発者に無料枠は無い**。投稿 $0.015/件、**リンク付き投稿は $0.20/件**。

- Zenn 記事へのリンク付き告知ポストは 1 件 $0.20。個人 MVP なら月数ドルで実害は小さいが、「投稿は無料枠で可」を前提にした難度・導入時期の評価は書き直しが必要
- 「定額制約」の趣旨は LLM のエージェント従量課金の回避であり、配信 API の微少な従量は別枠として許容する — という整理を明文化しておくこと
- 製品化時はユーザー数 × 投稿数で線形にコストが乗る点も P5 の経済モデルに含める

---

## 4. 【中】KnowledgeBaseAdapter の界面設計

- `updateStatus` / `listInbox` はストレージ抽象ではなく**ワークフロー概念**。ステータス機械（captured → processed → draft → needs-review → approved → published）をアダプタの外で明示的に定義し、各アダプタは「その状態をどこに永続化するか」（Obsidian: frontmatter / Notion: property）だけを担う構造にしないと、アダプタごとに挙動が割れる
- `query(filter)` を「RAG 入口」と呼ぶのはミスリード。メタデータ検索とセマンティック検索は別物。RAG をやるなら埋め込みインデックスは基盤の**外**（共通層）に持つべきで、そうすれば「Notion は全文取得が重い」問題も緩和される。`search(text)` はオプショナル capability として分離
- capability discovery（このアダプタは backlink / グラフをサポートするか等）を interface に入れておくと Notion 対応時の手戻りが減る

## 5. 【中】承認 UX の具体性不足

「通知 → frontmatter を approved に」は、Obsidian モバイルで frontmatter 編集が現実的でない以上、外出先で承認できない。

**代案: 承認を Git PR にする**。ドラフト生成 = PR 作成、マージ = 承認、マージを Actions が拾って配信。レビュー UI・修正コメント・履歴・差し戻しが全部無料で手に入り、GitHub Actions（§2）とも自然に接続する。LINE / Slack のボタン承認は製品化フェーズ送りで良い。

## 6. 【中】その他の設計論点

- **published コンテンツの SoT**: vault（プライベート Git）と Zenn 公開リポは別リポ。どちらを正とし、同期はどちら向きかを決めておく
- **モバイルキャプチャ**: Obsidian の弱点として挙げるだけでなく MVP 内で解を 1 つ決め打ちする（推奨: Obsidian Sync $4/mo、または inbox 専用の bot → Git 書込みブリッジ）
- **L6（メトリクス還元）**: X の read も従量（$0.005/件）。P4 以降なので MVP では「メトリクススキーマの定義だけ」と明記しスコープを締める
- **Notion 比較表の補足**: 公式 Notion MCP が成熟しつつあり「MCP 経由が必須 = 劣位」の差は縮小傾向。ただし定額適合・Git・ローカル速度で Obsidian 優位の結論は変わらない

## 7. 【軽微】

- Medium API 実質廃止・dev.to 推奨・Zenn の git push 公開は事実関係として正しい
- Note の Playwright 自動化は規約・UI 変更で破損リスクが高い。「ドラフトをローカルに整形して人間が貼る」半自動を先に置く方が安全
- 本ストリームと concept-forge 本体の関係（同居か別リポか）は未整理。アダプタ設計は `src/core/` の規約（フレームワーク非依存の純 TS + Zod 検証）と相性が良いので、別リポにする場合もこの規約は流用推奨

---

## 修正版の推奨アクション（Draft への反映順）

1. L0 を **CaptureAdapter 境界 + CapturedItem 正規化スキーマ**として再定義し、ChatGPT / Claude chat / Claude Code ログを取り込み経路として明記（実装は P4 でも、スキーマと冪等キーは P1 で確定）
2. 実行環境の比較表を `setup-token` 前提で書き直し、「① ローカル機」vs「③ Actions のみ」を改めて比較して MVP の実行基盤を確定
3. X の導入時期・コスト前提を pay-per-use で更新
4. ステータス機械を adapter interface から分離して定義
5. 承認フローを Git PR ベースで具体化
