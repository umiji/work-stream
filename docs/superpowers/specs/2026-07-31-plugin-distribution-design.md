# 設計: work-stream のプラグイン配布と knowledge-repo の GitHub 化

**日付:** 2026-07-31
**対象実装アイテム:** IMPL-L0-07（ユーザーレベル導入）
**対象要件:** REQ-N-08（全プロジェクトから使える）/ REQ-C-01（どの開発プロジェクトからでも登録できる）/ REQ-N-03（スマホだけで捕捉が完結する、のうち捕捉側）
**前提フェーズ:** P0-a（capture→digest 最短ループ）完了済み

---

## 1. この設計が解こうとしている課題

P0-a の完了時点で、`ws capture`（メモを正規化して knowledge-repo の `inbox/` へ冪等に取り込むコマンド）と、それを呼ぶ `/capture` コマンド・`/digest` スキルの**テンプレート**は揃っている。しかし次の 2 点が未解決である。

1. **どのプロジェクトからでも使えない。** テンプレートは `templates/claude/` にあるだけで、Claude Code が読む場所（`~/.claude/commands/` `~/.claude/skills/`）に配置されていない。`ws` コマンドも PATH に通っていない
2. **スマホから使えない。** 外出先で思いついたことを捕捉する経路が存在しない

当初この 2 つは別サブシステムとして分けて計画しかけたが、Claude Code のプラグイン機構を経路に使うと**ほぼ同じ作業で両方が満たされる**ことが判明したため、1 つのフェーズとして扱う。

---

## 2. 前提事実（2026-07-31 時点・公式ドキュメント由来）

以下はいずれも設計の根拠であり、変化した場合は設計を見直す必要がある。出典は `code.claude.com/docs` の "Use Claude Code on the web" および "Configure cloud environments"。

| 事実 | 設計上の意味 |
|---|---|
| リポジトリの `.claude/settings.json` に宣言したプラグインは、**クラウドセッション開始時にマーケットプレイスから自動インストールされる** | スマホからの利用がプラグイン 1 本で成立する |
| **ユーザー設定（`~/.claude/settings.json`）でのプラグイン有効化はクラウドに引き継がれない** | 宣言は必ず knowledge-repo 側にコミットする必要がある |
| リポジトリの `.claude/commands/` `.claude/skills/` `.claude/agents/` はクラウドセッションで読み込まれる | プラグインを使わずリポジトリ直置きでも成立はする（→ §5.1 で却下） |
| プラグインの `bin/` ディレクトリは PATH に自動追加される（本環境の PATH に superpowers・ecc・dev-dup-protect の `bin` が入っていることで実測確認） | `ws` の npm グローバルインストールが不要になる |
| クラウドセッションは Ubuntu 24.04 の使い捨て仮想マシンで、Node 20/21/22 が同梱される | Node ランタイム自体の導入は不要 |
| クラウドセッションはリポジトリを **GitHub からクローンする**。PR 作成にも GitHub が必要 | knowledge-repo の GitHub 化が必須の前提条件になる |
| クラウドセッションは Claude モバイルアプリから開いて対話できる | スマホからの捕捉経路が成立する |
| クラウドセッションの標準ネットワーク設定（Trusted）で github.com と npm レジストリに到達できる | マーケットプレイス取得が追加設定なしで通る |
| クラウドセッションでは `/plugin` コマンドが使えない（ターミナル専用） | プラグインの有効化を対話操作で行うことはできず、設定ファイルで宣言するしかない |

**注意:** Claude Code on the web は 2026-07-31 時点で research preview（Pro / Max / Team 向け）である。提供形態が変われば、スマホ経路は再検討が要る。

## 3. 設計

### 3.1 work-stream リポジトリ自身を Claude Code プラグインにする

work-stream を、プラグインの配布元（マーケットプレイス）とプラグイン本体を兼ねる構成にする。

```
work-stream/
├── .claude-plugin/
│   ├── marketplace.json          # 配布元としての定義
│   └── plugin.json               # プラグインとしての定義
├── commands/
│   ├── capture.md                # templates/claude/commands/ から移動
│   └── digest.md                 # 同上
├── skills/
│   └── digest/SKILL.md           # templates/claude/skills/ から移動
├── bin/
│   ├── ws                        # POSIX 環境用の起動スクリプト
│   └── ws.cmd                    # Windows 用の起動スクリプト
├── dist/
│   └── ws.mjs                    # 依存ごと 1 ファイルに固めた ws の実体
└── packages/
    ├── contracts/                # 既存。スキーマ定義の正
    └── cli/                      # 既存。ws のソースの正
```

`templates/claude/` は役目を終えるため**削除し、中身を `commands/` `skills/` へ移動する**。プラグインはこの位置を規約として読むため、テンプレート置き場を別に維持する理由が無くなる。

### 3.2 `ws` は依存ごと 1 ファイルに固めて同梱する

現在の `ws` は TypeScript のソースを `tsx` で直接実行しており、動作には外部ライブラリ（commander・zod・yaml・ulid）と TypeScript 変換ツールが必要である。プラグインの配布先ではこれらを取得する仕組みが働かないため、**esbuild で依存ごと単一の JavaScript ファイル（`dist/ws.mjs`）に固め、それを同梱する**。

`bin/ws` と `bin/ws.cmd` は、この固めたファイルを Node で起動するだけの薄いスクリプトとする。

**ビルド成果物をリポジトリにコミットする。** 通常はソースから再生成できる成果物を版管理下に置かないが、プラグインは配布時にビルド工程が走らないため、成果物が入っていなければ動作しない。ソースと成果物のズレを防ぐため、ビルドコマンド（`pnpm build`）をリポジトリのスクリプトとして用意し、「`packages/cli/src/` を変更したら再ビルドしてコミットする」という手順を README に明記する。

**却下した代替案:** 成果物をコミットせず、GitHub Releases のアセットとして配布し初回実行時にダウンロードする案。クラウドセッションの GitHub プロキシは「セッションに紐づいていないリポジトリのリリースアセット取得を 403 で拒否する」と公式ドキュメントに明記されており、knowledge-repo のセッションから work-stream のリリースアセットは取得できない。この時点で成立しない。

### 3.3 ノートの保存先の解決順序を拡張する

現在、`ws capture` は保存先（knowledge-repo の場所）を **PC 上の設定ファイル 1 箇所からのみ**読んでいる。クラウドセッションの仮想マシンは使い捨てであり、この設定ファイルは存在しない。

一方、クラウドセッションで開いているのは knowledge-repo そのものであるから、「いま作業しているリポジトリが保存先」という判定が使える。そこで解決順序を次のように定める。

| 順位 | 解決方法 | 主に効く場面 |
|---|---|---|
| 1 | 環境変数 `WORK_STREAM_KNOWLEDGE_REPO` | 一時的な上書き・テスト |
| 2 | カレントディレクトリから親方向へ辿り、`.work-stream.json` を持つディレクトリ | **クラウドセッション（スマホ経由）** |
| 3 | 設定ファイル `~/.config/work-stream/config.json` | **PC で他プロジェクトにいるとき** |
| 4 | いずれも該当しなければ、設定方法を案内するエラーで終了 | — |

順位 2 の目印ファイル `.work-stream.json` は knowledge-repo のルートに置く。内容は `defaultDomain` などリポジトリ固有の設定とし、保存先パス（`knowledgeRepo`）は持たない（自分自身を指すため冗長）。

**順位 2 を 3 より優先する理由:** knowledge-repo の中で作業しているなら、そこが対象であることは疑いない。PC で knowledge-repo を直接開いて capture した場合も、設定ファイルの内容によらず目の前のリポジトリに書かれるため、直感と一致する。

**却下した代替案:** クラウド環境かどうかを示す環境変数（`CLAUDE_CODE_REMOTE`）で分岐する案。判定すべきは「クラウドかどうか」ではなく「いまいる場所が knowledge-repo かどうか」であり、PC で knowledge-repo を開いた場合にも正しく働く後者を採る。

### 3.4 knowledge-repo 側に用意するもの

```
knowledge-repo/
├── .claude/
│   └── settings.json         # work-stream プラグインの宣言
├── .work-stream.json         # §3.3 順位 2 の目印
└── （既存の inbox/ notes/ moc/ articles/ profile/ log/）
```

`.claude/settings.json` には、配布元（work-stream の GitHub リポジトリ）とプラグインの有効化を宣言する。これにより、スマホからクラウドセッションを開いた時点で `/capture` `/digest` と `ws` が使える状態になる。

**knowledge-repo を GitHub の private リポジトリとして作成し push する。** クラウドセッションは GitHub からしかリポジトリを取得できないため、これが無ければスマホ経路は一切成立しない。private であることは、この時点では手順として担保する（機械的な監視は IMPL-L0-09 の範囲で、フェーズ P1）。

## 5. 却下した選択肢

### 5.1 プラグインを使わず、knowledge-repo に `.claude/commands/` を直接コミットする

リポジトリ直置きでもクラウドセッションでは動く。しかし **PC 側の「どのプロジェクトからでも捕捉できる」（REQ-N-08）が満たせない**。リポジトリローカルの設定は、そのリポジトリを開いているときにしか効かないためである。プラグインなら PC 側もクラウド側も 1 つの配布物で賄えるため、こちらを採る。

### 5.2 `ws` を npm のグローバルインストールで配布する

設計書 IMPL-L0-07 の当初案。プラグインの `bin/` が PATH に自動で入ることが確認できたため不要になった。加えて、クラウドセッションでは毎回グローバルインストールが必要になり起動が遅くなる。

### 5.3 `/capture` から `ws` を廃し、Claude Code 自身にファイルを書かせる

クラウドセッションでは knowledge-repo を直接開いているため、コマンドを介さず Claude Code がファイルを書くこともできる。しかし識別子の採番・重複判定・frontmatter 生成といった正規化ロジックが手順書側に散り、PC 経路（他プロジェクトから書く場合）と実装が二重化する。P0-a で「正規化スキーマと冪等キーを 1 箇所に固定する」ことを設計の柱に据えた経緯に反するため却下。

## 6. 本設計のスコープ外

- **Gemini からの自動取り込み**（IMPL-L1-04 gas-relay・IMPL-L1-05 ingress-issue）。Gemini アプリからの全自動化には Google Apps Script の中継と GitHub Actions の受け口が必要で、別フェーズとする
- **情報漏洩防止ガード**（IMPL-L0-09）。knowledge-repo が public に切り替わっていないかを機械的に監視する仕組み。フェーズ P1
- **取り込み処理の Git 抽象化**（IMPL-L0-02 runtime-git）。クラウドセッションでも通常の git コマンドが使えるため、本フェーズでは不要
- **`/scout` `/draft` コマンド**（IMPL-L3-02/03）。発信ネタ検出とドラフト生成。フェーズ P2

## 7. 未検証事項（実装中に確かめる）

1. **クラウドセッションから main ブランチへ直接 commit・push できるか。** 公式ドキュメントには「push はセッションの現在の作業ブランチに対してのみ動作する」とある。main で作業していれば通ると読めるが確証がない。通らない場合は、capture もブランチ作成 + PR 経由に切り替える（設計書の「承認 = PR merge」の思想とは整合するため、設計上の破綻にはならない）
2. **プラグイン宣言の設定キーの正確な綴りと構造。** 配布元の登録キーと有効化キーの正確な形式を、実装の最初のタスクで公式ドキュメントから確定させる
3. **`.work-stream.json` を置いた knowledge-repo で、`/digest` 実行時に不都合が生じないか。** digest は `inbox/` と `notes/` のみを対象とするため影響しない想定だが、E2E で確認する
